IntelliMeet Core Meeting Dossier

A code-traced comparison of IntelliMeet's meeting system against Google Meet-style behaviour, with a LiveKit migration architecture, API and schema design, security findings by severity, and a phased roadmap. AI translation features are deliberately out of scope.

Source read 77 files, all in full Stack React 19 · Express 5 · Mongoose 8 · Socket.IO 4 · raw WebRTC Verified by tsc, runtime probes, grep sweep Dated 5 September 2026

01Executive summary

Verdict. IntelliMeet has a solid authentication and user service, and a working two-to-four-person mesh WebRTC call. It does not yet have a meeting system. There is no Meeting model, no meeting API, and no server-side concept of a meeting existing before someone joins. Any string typed into the URL becomes a live room, hosting is awarded to whoever connects first, and the signaling server accepts every command from every socket without checking who sent it.

The core recommendation is to replace the custom peer-to-peer media layer with LiveKit and to put a real Meeting record, server-generated IDs, and a token-issuing endpoint in front of it. That single change resolves NAT traversal, reconnection, host mute and removal, scaling past four participants, and most of the WebRTC bugs found in the room page, while shrinking the frontend meeting code by roughly two thirds.

What is genuinely good

  • Express layering: Helmet, CORS, rate limits, validators, error envelope, graceful shutdown.
  • Registration with hashed OTP, verified email, Google sign-in, hashed reset tokens, JWT invalidation on password change.
  • Frontend auth pages call real endpoints with sensible validation and error mapping.
  • Perfect-negotiation structure and track replacement for screen share show real WebRTC understanding.

What blocks a credible demo

  • Meetings are not created anywhere. Rooms materialise on first socket join.
  • No socket authentication. No host check on kick or force-mute. Host is stealable.
  • STUN only, no TURN, no ICE queue. Calls fail on real campus networks.
  • Production build fails with 8 TypeScript errors. No tests exist.
  • Dashboard, scheduling, join validation, and settings are facades over localStorage.

Scope of this document. Everything below traces the actual code with file and line references. Findings marked verified were reproduced by running code, not only by reading it.

06Critical problems

Ordered by how badly each undermines the demo or the security story. Fuller security scoring is in section 19.

  1. Any URL creates a meeting. server.js:154-156 instantiates a room for whatever roomId arrives. Combined with MeetingRoomPage.tsx:303-316, which joins on mount, visiting /meeting/room/anything yields a working call.
  2. Hosting is a race and is stealable. First socket wins at server.js:162-166. Rejoining with another user's id at line 161 inherits their role. Sending { isHost: true } through toggle-media is merged verbatim at line 197.

  6. Build is broken. npm run build runs tsc first and fails with 8 errors: 7 Framer Motion variant typings in LandingPage.tsx:73-161 and the real bug at MeetingRoomPage.tsx:457. verified
  7. Password reset link poisoning. authController.js:438-450 builds the reset URL from the request's Origin or Referer header, which a non-browser client sets freely.
  8. Google sign-in links accounts without checking email_verified. authController.js:540-554.
  9. Preferences never save. Map-typed field plus dot assignment. User.js:114, authController.js:186-191,220-224. verified

07The meeting ID problem

Yes, random IDs create rooms today. There are three cooperating causes, and all three must change.

Cause 1: the server creates rooms on demand

// backend/server.js:152-156
socket.join(roomId);

if (!rooms.has(roomId)) {
  rooms.set(roomId, { participants: [], messages: [] });
}

There is no lookup against anything persistent because nothing persistent exists. The Map is the only registry, and this line populates it.

Cause 2: the room page joins on mount for any URL

// frontend/src/pages/meeting/MeetingRoomPage.tsx:303-316
if (status === 'idle') {
  joinMeeting({
    meetingId: meetingId || 'direct-join',
    title: 'CPEC Quarterly Review',
    ...
  })
  setTimeout(() => setStatus('active'), 800)
}

Direct navigation to /meeting/room/random123 is treated as a legitimate join. The connection hook then emits join-room as soon as the socket connects.

Cause 3: the join page validates only length

// frontend/src/pages/meeting/JoinMeetingPage.tsx:29-41
// Basic validation check (just length for testing flexibility)
if (parsedId.length < 4) { setError('...'); return }
setIsLoading(true)
setTimeout(() => { setIsLoading(false); navigate(`/meeting/lobby/${parsedId}`) }, 1500)

The "Verifying meeting…" button text is cosmetic. The lobby then hard-codes the title and forwards to the room.

Consequence for a LiveKit migration. If the token endpoint were written to mint a token for any room name the client asks for, the same defect would reappear one layer down, because LiveKit also creates rooms on first connect. The fix is not "validate in the frontend". The fix is that the backend refuses to issue a token for a meeting it cannot find in MongoDB.

Uniqueness is guaranteed by a unique index plus retry, not by probability alone. Collision probability for 106 meetings is about 3.5×10-3 across the whole lifetime of the deployment, and the retry loop makes even that harmless.

Generator

// backend/utils/meetingId.js
const crypto = require('crypto');
const ALPHABET = 'abcdefghijklmnopqrstuvwxyz';
const PATTERN = /^[a-z]{3}-[a-z]{4}-[a-z]{3}$/;

function generateMeetingId() {
  const bytes = crypto.randomBytes(10);
  let s = '';
  for (const b of bytes) s += ALPHABET[b % 26];     // tiny bias is irrelevant at 47 bits
  return `${s.slice(0,3)}-${s.slice(3,7)}-${s.slice(7,10)}`;
}
function isValidMeetingId(id) { return PATTERN.test(id); }
function normalizeMeetingId(raw) {
  const letters = String(raw).toLowerCase().replace(/[^a-z]/g, '');
  return letters.length === 10 ? `${letters.slice(0,3)}-${letters.slice(3,7)}-${letters.slice(7)}` : null;
}
module.exports = { generateMeetingId, isValidMeetingId, normalizeMeetingId };

normalizeMeetingId lets users paste abcdefghij, ABC DEFG HIJ, or a full URL and still be understood. The service loops on E11000 duplicate-key errors, which will essentially never happen.

User types a code or opens /meet/abc-defg-hij ↓ Frontend: normalizeMeetingId → null? show "That doesn't look like a meeting code. Codes look like abc-defg-hij." ↓ GET /api/meetings/abc-defg-hij (Bearer JWT) ↓ Backend: validator rejects bad format → 400 INVALID_MEETING_ID Meeting.findOne({ meetingId }) → null → 404 MEETING_NOT_FOUND // nothing created, LiveKit untouched status === 'ENDED' → 200 with status so the UI can show "This meeting has ended" bannedUserIds includes user → 403 PARTICIPANT_BANNED settings.locked and user is not host → 423 MEETING_LOCKED ↓ 200 → show lobby with real title and host name. Every rejection is terminal. The frontend never redirects to a fresh meeting, never generates a code, and the room page refuses to mount without a successful lookup result in state.

09LiveKit migration analysis

Decision: migrate. The custom mesh is not a bad piece of student work, but it is the wrong topology for anything past four participants, and every hard problem it currently gets wrong (NAT traversal, candidate ordering, glare, reconnection, host-side mute, screen share as a second track) is exactly what an SFU with a mature SDK solves for free. Explicit room creation versus lazy. LiveKit creates a room the moment a participant with a valid roomJoin grant connects, and deletes it after emptyTimeout. Because the security boundary is the token endpoint, which only issues tokens for meetings found in MongoDB, lazy creation is safe. The one reason to call RoomServiceClient.createRoom is to set options such as emptyTimeout and maxParticipants. Recommendation: call createRoom idempotently from the token endpoint the first time a token is issued for that meeting. It is one line, it is safe to repeat, and it keeps meeting creation itself a pure database write with no external dependency.

Which button. Two entry points: the "Start instant meeting" action in DashboardPage.tsx:28-31 handleStartInstant(), and the Create page's submit in CreateMeetingPage.tsx:38-70 handleCreate(). Role model

Two roles: HOST and PARTICIPANT. The creator is host, stored as Meeting.hostId. Role is computed server-side in the token endpoint as String(meeting.hostId) === String(req.user._id) ? 'HOST' : 'PARTICIPANT', written into the LiveKit token's metadata as {"role":"HOST"}, and re-derived on every host action by the requireHost middleware. The frontend reads role from participant.metadata to render controls, but every control's effect is a REST call the server authorises again.

Co-host. Not worth it for the FYP. It adds a coHostIds array, an endpoint to promote, and metadata refresh on live participants via updateParticipant. Two days of work for a feature examiners rarely probe. Put it in future work.

Leave versus end

  • Participant leaves. room.disconnect(), navigate to dashboard. No REST call. The participant_left webhook records lastLeftAt if you keep participant history.
  • Host leaves. Same as above. The meeting stays ACTIVE and hostId is unchanged, so the host can return with full controls. No role transfer. This is the simplest robust choice and matches how Meet behaves for the organiser.
  • Host ends for everyone. The confirmation modal that already exists at MeetingRoomPage.tsx:1133-1180 stays; its confirm button calls the end endpoint.
  • Everyone gone. LiveKit's emptyTimeout (recommended 300 s) closes the room and fires room_finished; the webhook marks the meeting ENDED. If the host wants to reuse the code the next day they create a new meeting. Trade-off: a meeting that empties for six minutes during a break ends. Raise the timeout to 900 s if that worries you; the cost is only an idle room on the server.

Token generation

// backend/services/livekitService.js
const { AccessToken, RoomServiceClient, TrackSource } = require('livekit-server-sdk');
const config = require('../config/environment');

const roomService = new RoomServiceClient(config.LIVEKIT_URL, config.LIVEKIT_API_KEY, config.LIVEKIT_API_SECRET);

async function createParticipantToken({ roomName, identity, name, role, screenShareHostOnly }) {
  const at = new AccessToken(config.LIVEKIT_API_KEY, config.LIVEKIT_API_SECRET, {
    identity,                       // String(user._id)  — stable across refreshes
    name,                           // user.fullName     — never client-supplied
    ttl: '10m',                     // only needs to outlive the connect handshake
    metadata: JSON.stringify({ role }),
  });
  const sources = [TrackSource.CAMERA, TrackSource.MICROPHONE];
  if (role === 'HOST' || !screenShareHostOnly) sources.push(TrackSource.SCREEN_SHARE, TrackSource.SCREEN_SHARE_AUDIO);
  at.addGrant({
    room: roomName,
    roomJoin: true,
    canPublish: true,
    canSubscribe: true,
    canPublishData: true,
    canPublishSources: sources,
    roomAdmin: false,               // host actions go through the backend, not the client
  });
  return at.toJwt();
}

async function ensureRoom(roomName) {
  return roomService.createRoom({ name: roomName, emptyTimeout: 300, maxParticipants: 50 });  // idempotent
}
async function removeParticipant(roomName, identity) { return roomService.removeParticipant(roomName, identity); }
async function muteTrack(roomName, identity, source) {
  const p = await roomService.getParticipant(roomName, identity);
  const pub = p.tracks.find(t => t.source === (source === 'camera' ? TrackSource.CAMERA : TrackSource.MICROPHONE));
  if (!pub) throw ApiError.notFound('Track not found', [], 'TRACK_NOT_FOUND');
  return roomService.mutePublishedTrack(roomName, identity, pub.sid, true);
}
async function deleteRoom(roomName) { return roomService.deleteRoom(roomName); }
Token lifetime
10 minutes. The token authenticates the WebSocket handshake; after that the session is server-side. Refresh re-requests a token, which is one cheap authenticated call.
Identity
The user's MongoDB id as a string. Same identity on refresh means LiveKit replaces the old session rather than showing a ghost.
Name
Account full name, set server-side.
Room
meeting.roomName, equal to the meeting code.
Role
Metadata, readable by every participant, which is how tiles know who to badge as host. Authority is still the backend.
Permissions
roomAdmin stays false so a leaked token never grants kick or mute. Those go through REST.

Chat

Today chat is Socket.IO with server-side history that the client discards. After migration the Socket.IO server is gone, so keeping it for chat alone means running two real-time systems for one feature. Recommendation: LiveKit data messages. localParticipant.publishData(bytes, { reliable: true }) reaches everyone in the room in order; RoomEvent.DataReceived delivers it with the sender participant, so the sender name comes from LiveKit, not from the payload. Late joiners will not see history; that matches Google Meet, whose chat is also session-scoped. If persistence is ever wanted, the sender additionally POSTs to a Message endpoint, and that is a P3 item. The existing ChatMessage type and the chat panel markup carry over unchanged.

Refresh, reconnect, multiple tabs

  • Refresh. App boots, auth store rehydrates, route /meet/:id/room mounts, useMeetingGuard re-validates, useLiveKitRoom requests a fresh token and connects with the same identity. LiveKit drops the stale session. Role comes back in metadata. No duplicate users anywhere because identity is the user id.
  • Network blip. The SDK emits Reconnecting, retries with backoff, then Reconnected; tracks resume. Show a banner. After the SDK gives up it emits Disconnected; offer a Rejoin button that re-runs the token flow.
  • Meeting ended during a blip. The room no longer exists; reconnect fails; the rejoin token request returns 410 MEETING_ENDED; navigate to the ended screen.
  • Multiple tabs. Same identity, so the newest connection wins and the older tab receives Disconnected with DUPLICATE_IDENTITY. Show "You joined from another tab or device." Blocking is unnecessary; replacing is the Meet behaviour.

Decisions

  1. Replace the custom WebRTC layer with LiveKit? Yes. The mesh cannot pass four participants or a campus NAT, and every host control you need is a one-line RoomService call on LiveKit. The migration also deletes the insecure signaling server.
  2. Which existing WebRTC code remains? None of the RTCPeerConnection, negotiation, ICE, or track-replacement code. What remains is the UI: tile markup, grid rules, control bar, chat and participant panels, modals, ended page, and the lobby's preview concept. Those are moved into components and re-fed from LiveKit hooks.
  3. Which parts are removed? MeetingRoomPage.tsx:82-276 and :321-447, useMeetingConnection.ts, lib/socket.ts, server.js:112-350, the store's participants and media flags, and the socket.io packages.
  4. Should meeting creation happen in MongoDB before the LiveKit room exists? Yes, always. Creation is a database write with no external dependency. The room is a runtime artefact of people connecting.
  5. Should a LiveKit room be created automatically when the first valid participant connects? Yes. Rely on LiveKit's lazy creation, gated by the token endpoint. Call createRoom idempotently at first token issue only to set emptyTimeout and maxParticipants.
  6. How are random IDs prevented from creating rooms? The backend is the only party that can produce a token, and it refuses unless Meeting.findOne({ meetingId }) succeeds and status is not ENDED. LiveKit cannot be reached without that token. The frontend additionally validates before showing the lobby, but that is UX, not security.
  7. Should only authenticated users create meetings? Yes. Ownership needs an owner.
  8. Should unauthenticated users be allowed to join? Not in this phase. Every route is behind protect, identity is the user id, and bans need a stable id. Guest join is a P3 extension: a guest endpoint that mints a token with identity guest-<random> and a supplied name, only when the host has enabled guests on the meeting.
  9. Best meeting ID format? Ten random lowercase letters displayed as abc-defg-hij, crypto-random, unique index, normalised on input, authenticated and rate-limited lookup.
  10. Where are host permissions stored? Meeting.hostId in MongoDB is the single source. It is projected into LiveKit token metadata for display and re-checked by requireHost on every privileged call.
  11. How are LiveKit tokens generated securely? Only in backend/services/livekitService.js using livekit-server-sdk with the secret from backend env, after protect, loadMeeting, ban and status checks. Ten-minute TTL, roomJoin for exactly one room, roomAdmin false, identity and name set server-side.
  12. Which host controls are realistic? Essential: remove, mute microphone, end for everyone. Recommended: turn off camera, remove and block. Optional: lock meeting, host-only screen share. Skip: waiting room, co-host, per-participant permission editing.
  13. Meeting state model? CREATED → ACTIVE → ENDED with endedReason. Add SCHEDULED only when scheduling has real UI.
  14. Chat: Socket.IO or LiveKit data channels? LiveKit data messages, reliable mode. It removes the last reason to run Socket.IO and gives you authenticated sender identity for free. Persistence is a later, separate endpoint if wanted.
  15. Minimum feature set before starting the AI translation module? Phases 1 to 5 complete: passing build, Meeting model and validated IDs, secure token endpoint, LiveKit-based room with audio, video, screen share, participant list, host mute, remove, end, leave, refresh and reconnect. The AI pipeline needs a server-side participant that can subscribe to audio tracks and publish data or audio back, which only exists once media flows through LiveKit. Building it on the mesh would have to be thrown away.
